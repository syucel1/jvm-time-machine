JVM Time Machine

Rewind a running JVM to any moment in the last 30 minutes and see what it was doing: threads, hot code, heap, GC, locks and in-flight requests. Built on JDK Flight Recorder, always on, at 2% overhead or less.

JFR-basedJava 17+Browser UIApache 2.0Production-safe

Summary & goals

A free, always-on "dashcam" for the JVM. It combines JFR, a profiler, periodic snapshots, request context and incident triggers on one time axis.

Problems it solves

Incidents vanish

By the time someone attaches a profiler, the spike is over.

JFR has gaps

No request view, no time diff, no automatic incident capture, no fleet view.

Profilers are for dev

JProfiler and YourKit are excellent, but they aren't made to run always-on in production.

Goals

01

Dashcam

Rolling 30-min buffer, frozen when a trigger fires.

02

Scrub

Full JVM state at any second on one timeline.

03

Diff

"What changed between A and B?" as differential flame graphs.

04

Request replay

Rebuild one request's life from its trace ID.

05

Explain

An incident summary readable in 2 minutes, optionally AI-written.

Non-goals & constraints

v1 does not do full deterministic record-and-replay, does not replace APM/metrics platforms, and does not support non-JVM runtimes.

LicenceApache 2.0, only free dependencies
DeploymentSingle-JAR agent; works without the collector, writing to local disk

Architecture

Three tiers: tm-agent in every JVM, a tm-collector service, and clients led by the browser UI. Data flows one way; the agent keeps working if the collector is down.

Data model

Everything is an event on one shared time axis, keyed by (jvm_id, timestamp, thread_id) and optionally trace_id. That one key is what makes scrubbing, diffs and request reconstruction cheap.

TableGrainKey columnsSource
eventsOne row per JFR eventjvm_id, ts, duration, event_type, thread_id, stack_id, trace_id, attrsJFR, custom events
stacksOne row per unique stackstack_id, frames[]JFR, async-profiler
snapshotsOne row per snapshotjvm_id, ts, kind, payloadSnapshotter
incidentsOne row per trigger fireincident_id, jvm_id, ts, rule, window, artifacts[]Trigger engine
artifactsBlobsheap dumps, raw .jfr, flame graphsObject storage
Raw .jfr chunks are always kept, so any window can be exported and opened in JMC or JProfiler. Stacks are deduplicated by hash. Retention: 30 min on the agent, 7 days in the collector, incidents until deleted.

UI decision: browser, not Swing

The core interaction is dragging a scrubber over millions of events and redrawing flame graphs at 60 fps. That needs GPU-backed Canvas/WebGL, which is mature in browsers. Sharing an incident by URL matters for on-call teams.

Browser (React + Canvas/WebGL)Zero install, one UI everywhere, share by link, best charting libraries, embeddableNeeds a server process; large timelines need virtualisationChosen

Key flows

1 · Continuous recording

  1. Agent starts JFR with timemachine.jfc and a RecordingStream.
  2. Every 10 s, snapshots are added as custom JFR events in the same stream.
  3. Chunks roll in the 30-min disk buffer; the shipper streams them out if a collector is configured.

2 · Incident trigger

  1. A rule matches, e.g. gc.pause > 500ms or p99(http) > 2s.
  2. Agent freezes the last 30 min and boosts detail for 2 min.
  3. Writes a .tmz bundle (JFR + snapshots + metadata) and ships it.
  4. Analyzer builds the report and notifies Slack/webhook.

3 · Timeline scrub

  1. UI loads per-second aggregates for the window.
  2. On drag, it fetches that second's threads, stacks, requests and events.
  3. Detail is fetched lazily and cached for smooth dragging.

4 · Time diff

  1. User picks window A (normal) and B (bad).
  2. Analyzer aggregates samples per stack, normalises by duration, subtracts.
  3. UI shows a differential flame graph and event deltas.

5 · Request reconstruction

  1. User pastes a trace ID from logs or APM.
  2. API selects events with that trace_id plus same-thread events in its span.
  3. UI draws a lane per thread with SQL, HTTP and lock spans.

Overhead & safety

Budget: ≤ 2% CPU in steady state. Anything heavier than JFR defaults is sampled, or runs only after a trigger fires. Costs below are estimates to verify in benchmarks.

SourceModeEstimated cost
JFR default eventsAlways on~1%
Extra JFR events (allocation sampling, I/O ≥ 20 ms)Always on+0.3–0.5%
SnapshotterEvery 10 s< 0.2%
Context instrumentationChosen packages< 0.3%
async-profiler wall-clockTriggered, 2 min2–5% while active
Heap dumpTriggered, max 1/hour, opt-inPauses for seconds

Circuit breaker

Agent CPU > 3% for 60 s → drop to plain JFR and report it.

Bounded memory

32 MB shipper queue; drop the oldest data, never block app threads.

Privacy

Arguments, bind values and bodies are off by default; SQL literals are stripped.

Kill switch

JMX TimeMachine.stop() or a config flag leaves only plain JFR.
